# 天文本命结果的缓存与迁移设计

2026-09-20，研究阶段设计；尚未实现。范围是用户已选择的七政四余与中国二十八宿，共享出生资料和天文基础，但分别保留计算依据。生肖、宿曜关系不在范围内。

## 输入与旧资料

现有 `BirthProfile.date` 将钟面按固定UTC+8解释。新计算必须复用这个物理时刻，不能因为字段写着 `Asia/Shanghai` 就改为包含历史夏令时的另一种解释，也不能加上八字使用的真太阳时偏移。保存原始钟面、`fixed-utc-plus-8-v1`解析政策和派生的UTC时刻，验证三者一致。

经纬度不足不妨碍地心七曜。旧资料的纬度保持未知，不填默认值；只有需要地平、宫位或地面视差时，才要求用户确认经纬度。海外钟面与历史时区输入是独立迁移，不在本批顺便放开。尚不能确定的时间不能被AI补齐。

## 模块与缓存契约

沿用 `SavedState` 存储，先新增 `natal-astronomy:<account>` 旁路缓存，保留现有 `natal:<account>`。旁路外壳保存 `schemaVersion`、owner、原出生资料指纹、创建时间、payload及摘要；摘要用于检查损坏，不表示服务端认证。

| 结果 | 真正的计算输入 | 必须绑定的版本 |
| --- | --- | --- |
| 地心七曜 | 规范化出生时刻 | 星历实现、时间尺度/ΔT、坐标系、天体修正口径 |
| 二十八宿 | 七曜坐标、距星表及其时间变换 | 距星身份集、星表与历元、自行/岁差/章动政策、赤道或黄道宿界规则、角度单位 |
| 七政四余 | 共享七曜、经核定的四余与宫度输入 | 选定流派、每项四余历元/公式、安命/宫位规则及实际需要的出生地点 |

每个模块保存自己的 `moduleID`、`methodVersion`、`inputFingerprint`、`dependencyVersions`、`sourceIDs` 和确定性结果。七曜基础已就绪不能把七政四余模块标成完整；规则未核定的模块不生成成功结果。

首轮仍以整个实际引擎哈希作为保守失效条件，再校验各模块版本；版本精细化到“只重算受影响模块”另行实现，不能声称今天的全局 `engineRevision` 已经做到这一点。依赖不匹配或资料修改时重建；重建失败时保留旧资料但标为失效，不把旧结果注入新问题。

## 生命周期与问答

1. 登录并确认出生资料后，复用当前八字紫微建档流程，再按已上线模块的能力建立天文缓存。共享同一出生时刻的七曜计算只执行一次。
2. 并发请求沿用现有建档任务合并与scope校验，账户切换或资料变更后，旧任务不得写入新账户或新档案。
3. 只有Swift侧读取、验摘要和版本后的缓存可以传进桥接层。模型参数、聊天历史、用户导入文件均不能冒充当前可信本命缓存。
4. 问答工具按需读取已验证模块的有限结果和依据，不把整套本命盘反复塞入每条消息。已知六爻工作区存在容量待验问题；新增工具必须通过实际Swift→后端传输预算检查。
5. 明确请求某日星位、行运或问事时，使用独立reference instant计算动态层，不覆盖出生结果。流年图不能以“本命缓存命中”跳过计算。
6. 删除账户本地资料、替换笔记和出生资料修订，均要清理或失效相应旁路；普通导入的可重建快照不作为事实恢复。

## 结果与边界

对每颗七曜分别保存对象、坐标、单位、frame、UT/TT及政策。二十八宿结果必须能追溯到某颗距星和下一颗距星；宿界区间采用左闭右开，0/360环绕独立处理。先验证一整圈的顺序与覆盖，再做归宿，避免把逆序造成的负宽度取模成近360度的错误宿区。

边界附近需同时考虑出生时间的不确定区间与星历/星表误差。未提供出生时间精度不能伪称“确定不会跨宿”；结果可给参考归宿及边界距离，显示已知的不确定性。月亮所在宿使用明确对象名，不自动称为命度。

## 上线前必须验证

- 旧资料迁移前后UTC、八字和紫微结果不变；无纬度仍可使用地心星位，要求地点的计算明确缺项。
- 缓存命中不重算；更改出生资料、星历或距星版本后确实失效；跨账户、损坏、旧版本与模型伪造快照被拒绝。
- 独立复算覆盖七曜、时间边界、闰日、逆行附近、宿界两侧及觜参距星改定反例。共享TT验证不得替代真实输入时间政策验收。
- Swift/JavaScriptCore与Node契约一致；完整结果及引用可以经现有AI传输限制恢复；知识解释只能引用已经上线的计算对象。

当前可推进七曜基础与距星研究；四余、安命度、完整28距星表和时间政策尚未选定，不能把这份缓存设计当成完整排盘验收。
