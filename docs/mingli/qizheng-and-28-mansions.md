# 七政四余与中国二十八宿：首版范围与研究顺序

2026-09-20。用户调整优先级：现在启动扩展研究与设计；明确选择中国二十八宿、本命星宿与传统星度，不选择宿曜关系体系，不加入生肖。原有核心缺口继续记录，不能把优先级调整写成核心已全数验收。

## 当前仓库事实

- 已有登录、出生资料确认、按账户缓存本命档案。八字与紫微本命计算结果保存后供问答复用，动态层另算。
- `BirthProfile` 保存城市、经度和 timeZoneID，但没有纬度；当前校验只允许 Asia/Shanghai，年月日时分实际按固定 UTC+8 解释。它不是支持全球历史时区的出生资料模型。
- 当前 natal schemaVersion=1，birthKey包含出生年月日时分、性别、经度及时间口径。整个档案与引擎版本绑定。不能给现有档案直接补一个星宿名称就当作新的完整排盘。
- 研究环境已有 Astronomy Engine 2.1.19，包清单声明 MIT；它用于过往独立历法检查，尚未成为产品依赖。现有 lunar-javascript/iztro 本身不构成七政四余与星度的完整实现。
- 核心最后远端通过版本为 f13e12c；三合B5b代码与资源在工作区，专项Engine验证已做；全量复核771项通过、1项原始回执容量测试失败（48,901 bytes超过该测试45,000预算），不可称本批验收通过。Swift专项34项通过；全量/真实传输容量/独立审查/远端验收未完成。奇门E2b仍未解决。

## 推荐架构

继续采用本地确定性计算，复用SwiftUI与JavaScriptCore桥接，建立一个共享天文计算基础，再由两个模块分别解释。固定本命结果按账户保存；出生资料、星历、距星表或流派规则版本改变时使相关结果失效。问答读取已保存结果，只有明确请求行运/当下星位时才计算动态层。

另两个可选方案是服务端星历计算和第三方排盘API。服务端便于集中维护较大的星历数据，但增加联网与出生资料传输；第三方API接入较快，但计算约定与反例验证取决于供应商。首版先评估本地方案，独立复算参考可以采用另一个实现；不把同库两次调用当独立验证。

## 共享出生与天文基础

1. 保存出生原始钟面与明确时间口径，规范化到物理UTC时刻。原有资料继续按已声明的UTC+8解释，不因新时区功能悄悄改盘。海外输入与历史时区支持单独评估范围；时区歧义不可自动猜选。
2. 补出生地纬度及地点确认。经纬度是地平/宫位与可能的视差计算输入；地心七曜星位不应被说成必须依赖地点。旧资料只有经度时不填默认纬度伪装完整。
3. 记录星历来源、版本、时间尺度、地心/地面观测口径、参考坐标系及历元。出生真太阳时不能再次移动真实天体计算时刻。
4. 每个模块拥有独立计算政策与出处；八字用太阳时、紫微历法边界和新模块的星位计算分别保留，不混成一个无说明的钟面。

## 中国二十八宿首版

用户已选定此方向。首先建立28宿与距星的可查证表，记录星表身份、历元、坐标与来源；采用哪一种传统宿度口径须读原典和对照资料后确定。不能把二十八宿等分成28个扇区，也不能直接使用现代88星座边界替代。

推荐首版展示出生时月亮所在宿、入宿度、该宿范围及边界敏感性，并提供七曜入宿的共享计算。使用“出生月亮所在宿”这个明确对象名称；是否另称本命宿/命宿，以及命度取法，须随选定流派确认。农历日期查表的值日宿不是这项天文入宿计算，宿曜27宿关系也不在首版中。

距星赤经所划的赤道宿度、黄道位置及传统度量单位需分别定义和验证，不能把黄经差、赤经差、古度和现代角度相互替换。每个结果附具体宿、对象、角度、口径、版本、来源及边界状态；靠近宿界时说明输入时间误差可能改变归宿。

## 七政四余首版

先验证日、月、水、金、火、木、土的本命星位，再按选定流派定义十二宫、宫度/命度和入宿关系。七曜、十二宫与二十八宿共享天文位置，但不从八字或紫微标签推算。

罗喉、计都、月孛、紫炁需逐一确定计算定义、历元、运动公式与来源，不能把四余全当实体行星，也不能把天文库的交点/近远地点事件接口直接当作传统四余公式。现代星历是否替代某流派古历、交点采用何种约定、紫炁如何推算，都是上线前必须解决的计算选择。

第一阶段只验收可追溯本命排盘、盘面说明与固定档案。完整行限/流年断法、自动吉凶和多个流派汇总评分不与基础排盘绑成一次大交付。后续解读需逐条绑定原盘对象和所选典籍依据。

## 当前资料核验边界

网络恢复后已取得《張果星宗》《星命溯源（四库全书本）》提要及卷一的实际转录正文。归档见 `native/Engine/validation/research-qizheng/source-scope-review.json`；主代理独立复核了3份文件的字节哈希及27处引文的文本、Unicode/UTF-8偏移和行号。

《張果星宗》确有七曜和四余算法正文，不能再写成只找到目录。但所读传本的命度图与授时过宫图缺失，四余所用“积日”起点未获明确，罗喉段有残句，紫气的粗略行速与后文算法也不完全一致。它可用于界定原理和发现缺口，尚不足以直接生成生产公式。月躔之处与命度取法须分别处理，不能给出生月宿换个名称便当成完整命度。

二十八宿的研究又确认了距星沿革问题：历史距星表与明清改定后的距星表不能混用，尤其是奎、觜、参。取得了国家天文台作者的《二十八宿的形成与演变》正文、带版本号的维基百科文献线索，并通过VizieR读取了觜参相关4颗星的Hipparcos坐标、通过SIMBAD核对了星表身份。材料及限制见 `native/Engine/validation/research-qizheng/mansions-source-review.json`。

真实星表反例已复现：旧觜距星φ¹ Ori到旧参距星δ Ori的赤经差约为−0.7035°，盲目取模会把它变为359.2965°；改定后的λ Ori到ζ Ori约为1.4052°。这说明“沿传统名称顺序直接做差再取模”会吞掉几乎整圈，必须先校验距星版本与一周覆盖。Hipparcos返回列的历元是J1991.25，SIMBAD本次返回的是J2000，脚本分别计算，未混用两者。可用 `check-mansion-counterexample.py` 复跑。上述材料仍不等于已经校定全套28颗距星、出生时视位置变换或某一七政四余流派。

## 七曜可行性复算结果

可复跑的研究脚本、两套坐标和原生输出已归档到 `native/Engine/validation/research-qizheng/ephemeris/`。研究依赖与产品隔离，未修改App依赖、桥接命令或排盘输出。

- Astronomy Engine 2.1.19与独立Swiss/Moshier实现比较1901–2100年每季的5,600组七曜位置。预先设定的可行性阈值是每坐标60角秒。
- 各用默认时间模型时有13组超阈值，最大74.05角秒，全部为2093年以后的月亮。对2100年ΔT的估计差异最高约111秒。
- 控制为同一TT时间后，5,600组均在原阈值内，最大21.49角秒。这个控制实验解释时间模型造成的差异，不证明任何一种未来ΔT预测正确，也不提供全时段精度保证。
- Node与真实macOS JavaScriptCore的5,600组输出最大差异约5.7e-14度；七曜的同一时刻三种时区写法完全一致。运行时一致性与独立星历验证分开记录。
- 候选浏览器库约116KB、gzip约47KB，MIT；Swift运行兼容。独立参考pyswisseph声明AGPLv3，仅在临时研究环境运行，不作为产品依赖。

因此本地七曜计算方案值得继续，但生产首版必须明确UTC/UT1/TT政策、月亮修正口径和宿界误差处理。出生真太阳时不能用于再次移动星历的物理输入时刻。
