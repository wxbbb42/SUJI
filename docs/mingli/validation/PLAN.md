## 验证准则

- Node ↔ JavaScriptCore parity 只验证移植一致性，不证明原算法正确。
- 同一底层库的两个包装不算独立 oracle；实现分歧必须追到规则或历法来源。
- “专业准确”指符合公开记录的计算与所选传统规则；不把传统解读的预测效力当作已获科学验证。
- 大运/格局/强弱等存在流派或工程决策时，保留规则版本、出处、前提和限制。
- 不用降低范围、移除出错系统或仅显示免责声明替代实际算法修复。
- 研究不宣称穷尽互联网；最终库存需列出检索覆盖、成熟度标准、遗漏/不可访问资料。

## 验收中发现的第二层问题

- 两轮live回答发现工具被反向引用、食神伤官混淆、健康映射及按年份安排升职；不能用HTTP成功或免责声明判通过。基线回答原样归档。
- 工程规则曾把远隔相合视为成化、两支视为完整三合/三会、非禄刃月的比劫误命名；已补柱位/缺支/候选状态及反例。
- 成功起盘后的模型容量异常曾让重试重新起盘；现先保存receipt，错误也纳入容量。外部导入去除计算身份，历史仍可阅读。
- 校时原有「紫微大限转十神」混合两种体系，已改为真实紫微大限宫位/星曜及虚岁事实；八字交运按精确日期。
- 草稿核验是一层模型质量控制，不是准确性oracle；不通过时保留原盘、展示只摘录实际工具数据的事实回信并可同盘重试，不展示未核对草稿。
