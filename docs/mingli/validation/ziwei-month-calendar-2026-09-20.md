# F5 — 真实农历月份与流月排盘月序

## 修复对象

`native/Engine/validation/reasoning/core-d5-results.json` 保留真实 DeepSeek 错误及审核放行记录：2025-08-08、2025-08-09 的工具结果都是 2025 年闰六月（十五、十六），只有所选流派的排盘月序从 6 变为 7，回答却概括为“农历月序号从6月进到7月”。原档案未修改，未重新生成一个更容易通过的草稿。

本批选用有严格适用范围的本地矛盾检查，接入现有 `ReadingVerifier` 的先修正、再审核流程。没有替换整份回答或改变用户所问时间层。未修正的原错误在第二次本地检查时会拒绝展示，模型的 `accepted=true` 不能覆盖已成立的矛盾。

## 适用范围与依据

- 首段明确给出两个不同公历日期并指定紫微流月，全文其他数字日期只能属于这一对。支持完整中文数字日期、同年省略第二个年份及 ISO 日期；没有继承依据的日期、第三日期、斜杠/“号”等未解析日期、数字农历日期均不授权修正。
- 每个日期须有唯一身份且调用在结果之前的 `get_ziwei_timing(date, withMonthly:true)` 回执。参数、正午查询模式、参考时刻、民用/计算日期、月历字段和所选历法/排盘方法须完整相符。相同日期多个回执必须一致；缺项或冲突不能取其中有利的一份。
- 仅当实际农历年、月、闰标记相同而排盘月序不同，且肯定陈述明确把该 6→7（或其他可支持月序）变化称作真实农历换月时修正。保留原调用 ID、原 JSON 路径及字段值，不另算历法，不改四化或星宫。
- 方法为 `ziwei-monthly-selected-v1` / `suji-ziwei-monthly-1`：iztro 2.5.8 / lunar-lite 0.2.8 normal 约定，闰月 1–15 日取当月，16 日起取下一排盘月。两份上游版本化引用 URL/SHA256 必须匹配 D5 已审阅的原文。它不是各流派通例。
- 传输可复用较早回执的相同来源书目。只接受完整、明确日期的流月回执提供的原始书目，同一来源 ID、版本和数组位置；不追引用链，不接受前向引用、重复身份、先结果后调用或与引用并存的损坏字段。该窄范围不接受其他工具或即时查询的书目来授权修正。
- 否定、引述、转述、假设、问句和其他日期保持原意，不截取肯定片段来要求改写。

这是已观察到错误的有限语法检查，不是中文语义正确性的证明。首段缺少日期对、其他合法查询模式、实际换月、其他流月措辞或额外日期的解读仍走原流程，不能称为已经全面核验。

## 验证

1. 永久回归先在原版本得到 0 条检查意见而失败，再验证新版本返回带两份日期/原值的修正意见；修正稿不触发该意见。独立复查发现的日期、转述、引号、回执顺序及书目复用反例也先复现失败再修正。
2. 12 个新增 Core 测试覆盖原始真实失败、文字和证据反例、同日期冲突及实际 JavaScriptCore 工具路径。出生档案只构建一次；两个日期投影得到原始月份 6/6、闰标记 true/true、排盘月序 6/7。正常传输、持久化后恢复和重试的检查意见相同，重试新增计算次数为 0。
3. 独立 39 项探针复查，最终 0 个不符；包含真实精简传输、完整书目提供者、损坏或空的内联书目、错误来源/版本/哈希/位置、重复身份、时序和引述范围。
4. 新增可选 `ziwei-monthly-replay` 评估案例，用原档案中的问题、草稿、工具历史和两份回执调用真实 Swift `ReadingVerifier` / `ChatClient` / 后端 handler。两次实际 DeepSeek 请求依次为修正和审核，没有重新计划、排盘或生成初稿。原文 SHA256 及上述输入逐项一致。新记录在 `core-f5-replay-results.json`。
5. 独立人工核对修正答案：两天仍为闰六月十五/十六，6→7 被明确称作排盘月序变化；斗君田宅巳、流月命宫财帛戌→子女亥、月干支癸未→甲申和两日共 8 条四化均与原回执相符，未再暴露 `effectiveMonth`。

真实回放只使用合成出生资料，认证和配额为评估夹具，不能称为已部署 Supabase 端到端验证。模型修正时删去了原答案中非本题必需的生年/大限/流年背景段；本批不宣称模型能逐句保留所有未修改背景。摘要仍把完整“癸未/甲申”简称为“月干”，应视为文字精度局限；不能据此扩大为完整紫微解读验收。

完整 Core、原生编译和精确远端提交的 CI 验证结果在主计划中记录。核心阶段 G 尚未验收，不进入七政四余/独立星宿实现。
