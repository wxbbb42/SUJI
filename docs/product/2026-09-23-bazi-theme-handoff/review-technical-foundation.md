# 八字主题衔接：独立技术与 AI 证据基础评审

日期：2026-09-23。评审者：独立 agent `/root/theme_ai_audit`。基线提交：`776b34f`。本评审先读取当前源码及上轮 AI 证据评审，未参与主题内容或业务实现，未运行模型、修改业务代码或提交。下面的反例与验收项目是实现要求，**不是已经运行通过的结果**。实现后的复核应另列，不覆盖此基线记录。

## 判断与最小可交付路径

可以做一条有实际价值的小闭环，但不宜现在建设四体系通用 EvidenceBroker。最小路径是：册页选择已审主题 → 持有本机主体与资料版本的意图绑定 → 原问道保留草稿、显式确认发送 → `AppStore.request` 真正执行现有本地 `get_domain` 投影 → 从当前可信档案及本轮真实回执重建闭合主题目录 → 模型选择有限解释/追问动作 → 程序核验并完整渲染 → 关联来源、保存与返回册页。

`get_domain` 执行不等于重复排盘。`AppStore.request` 已通过 `ensureNatalDossier` 复用有效本命缓存。本轮产生新的投影回执，保留本次提问时间；旧快照和旧回执不改写时间，不伪造一次不存在的工具执行。AI 可以帮助选择当前困惑最相关的审定内容，但不拥有改写事实、删除限定、虚构用户处境的权限。

若使用闭合主题 renderer，应在生产路由中明确它与已有 `ReadingVerifier` 的关系：这是独立的确定性核验协议，和现有 `BaziFrameworkReading` 一样，不是“跳过核验”。真实验收必须调用这个生产 renderer/validator；如果仍开放任何自由命理正文，那些文字必须进入原核验器，且不能把一次 `accepted=true` 当作语义绝对可靠的证明。

## 阻塞这条新链路的发现

### T-01 · P1：绑定不能等同证据，报告全文或自制回执都不能授信

依据：`native/App/Services/ChatSession.swift` 当前第109—130、146—183行；`native/Core/Sources/SujiCore/ReadingContext.swift` 的 `history`；`BaziFrameworkReading.swift` 的 `plan/catalog`；`ReadingDocument.swift` 的 `trustedPrevious`。

当前旧回执必须与本轮 `ToolContext` 完整相等。新主题入口如果仅把快照 ID、来源列表或报告文字拼进系统提示，旧核验器不会验证这些新绑定。把它包装为 `ToolReceipt` 又会冒充真实执行。

**反例：**前一天的主题→今天追问；导入文件里附一份完整 JSON 主题；已换账号但生日相同；报告里是正印，用户提示“沿用这个依据把正印称为七杀”。这些都不能凭文字或哈希建立新事实。

**建议合同：**导航意图至少含本机 owner、subject/birth revision、完整出生指纹、bundle revision、payload revision、snapshot ID、content/rule version、theme ID。它只选择主题，不携带可直接信任的模型事实。发送时从当前仓库重新验证该身份，并经现有工具执行路径取回事实；构建主题目录时逐一比较所用 pointer/value 和规则条件。给模型的内容只包含本主题必要字段、审定 rule ID 与允许的动作，不发送整篇报告或全部档案。

**验收：**上述身份各改单一字段须先于模型调用拒绝；跨日静态追问有效而原回执不变；替换任一主题依据值/来源 ID 后不能渲染；正常本机缓存复用需有真实执行回执而不是构造成功 fixture。

### T-02 · P1：出生 A→B→A 会绕过只比较最终出生值的异步检查

依据：`AppStore.swift:updateBirth` 第214行附近只更新 birth，不更新独立出生 generation；`ChatSession.checkScope`、`ReflectionSession.checkScope` 仅看 scopeRevision 与最终 birth；报告身份也依赖这两项。

**反例：**A主题开始在线回答→修改为B→再改回A→第一次A的请求晚到。账号scope没有变化、出生值又等于A，旧工作可能恢复为当前答案。主题待发送 intent 也会遭遇同样歧义。

**建议：**添加独立且不可复用的出生确认 revision/generation，成功保存出生变更后轮换；ChatSession、ReflectionSession、主题待发送绑定以及相关异步持久化捕获它并在每次 await 后、写入前检查。不要只借用 scopeRevision：现有 `ChatView.onChange(scopeRevision)` 会清空 input，根壳也用它控制 Profile，资料失效和草稿处理需要分开。完整跨设备多版本事务可延期，但在本轮声称支持“资料变更”前，运行时 ABA 保护和重启后的旧 intent 验证必须闭合。

**验收：**A→B、A→B→A、账号甲→乙→甲，在网络返回/本地投影返回前发生时，不允许写入旧结果。原输入仍可找回；当前报告可本地重建；不能仅依靠测试设置一次不同的生日覆盖 ABA。

### T-03 · P1：静态追问授权必须有路由边界，而不是主题挂上后永远沿用

依据：当前 `BaziReadingRequest.resolveRequest` 对既有框架采用窄词句规则，依赖上一条通过回执重建的结构化文档；`TodayReadingRequest` 和 `ReadingFactRequest` 是另两条路径。它们没有通用生活主题的语义权限。

**正例：**“这里说的约束是什么意思”“这两个条件为什么要一起看”“简短一点”可保持本命范围。

**反例：**“明年还会这样吗”“我对象也是吗”“今天该不该辞职”“那合适吗”“别聊八字了”“他说我根本不是这样”。分别涉及时间、他人、具体事件、指代不明、退出主题、用户现实反证。不能用一份本命条目回答这些问题，也不能自动为事件起卦。

**建议：**请求解析输出显式枚举：本主题静态、动态、他人、事件、模糊、退出。静态只允许有限语义动作；动态走原必要取数，事件遵守现有明确起盘和确认门槛；他人缺主体资料或“合适”缺对象时正常澄清。否定、引用、混合句要纳入反例。无法识别可返回澄清或回原通用管线，不能默认为静态命理许可。

**验收：**连续三个静态追问，随后跨主题/日期/他人/事件，再“刚才那个”不能自动使用已经失配的绑定。重试保持原题冻结时间及原工具，不能每次重试刷新“今天”。

### T-04 · P1：有来源的词义不等于有来源的现实人格，条件和正文必须作为同一单元

依据：`ReadingVerifier.feedback` 对协议正确、`accepted=true`、空issues会接受；确定性语言守卫只覆盖有限已知句式。`BaziFrameworkReading` 通过闭合 claim ID 和固定正文解决特定范围问题，不能外推为任意中文安全。

**反例：**工具只有十神关系，AI写“所以你总是在替别人兜底”；受审条目只有“若实际生活中出现这种情形，可尝试……”，AI删掉前半句；正印与伤官并见被改写成“你天生适合研究”。加“传统上/可能/仅供参考”不补足条件。

**建议：**本轮主题把盘面事实、传统条件关系、现代自我观察练习明确分层，闭合渲染单位包含必要前提、冲突/不适用、来源和正文。模型返回结构化选择，不返回可直接展示的命理推断文字。现实信息只能引用当前用户明确给出的内容，引用应有turn/span，不能从“你看起来”造经历。若暂不做span协议，MVP不让模型生成新的用户事实断言。

**验收：**恶意/错误模型选择不存在ID、重复ID、错误版本、漏条件、注入新正文、选互斥分支时被拒绝或有限修复；普通问题仍得到与本盘差异相关的完整段落。计数应区分计算成功、选项核验通过、内容达到用户问题三个维度。

### T-05 · P1：新绑定/文档必须加入本地回放与外部导入的不同信任合同

依据：`ArchiveCodec.swift:removingImportedReceiptTrust` 会去掉 toolContext、analysisMode、readingDocument；本机 SavedState 直接 JSONDecoder，保留可信上下文。`ReadingDocument.isValid` 只是结构检查，可信追问还需 `trustedPrevious` 从回执重建、逐项比对。

**反例：**把合格主题文档 JSON 改为更肯定正文再从文件导入；旧本地文档内容库版本撤回后继续作为新问答证据；归档只存正文却误把“返回册页”重新指向新生日下的同名主题。

**建议：**新 themeBinding/themeDocument 在外部导入时显式去信任；可读历史保留，但不自动进入当前证据。可信本地回放至少校验source user ID、context、主题/规则/内容版本、所用工具回执及完整渲染结果；不能只检查JSON可解码。旧文档需要显示“当时资料/解释版本”，返回当前报告时重新核对身份，失配则提供可理解的重新进入动作。

**验收：**保存重启、外部导入、篡改正文、规则版本改变、资料改变、已删除来源，每个都覆盖；正文可读不等于允许发起可信追问。

### T-06 · P1：ReflectionSession仍是自由流式旁路，新主题不可通过它实现“继续问”

依据：`ReflectionSession.swift` 第50—61行直接流式显示并保存；`SujiApp.swift` 的今日反思传入 `profile.daily`；`ObservationViews.swift` 传校时与关系结果。已有scope/birth隔离，不应说它完全没有保护；它缺少的是命理证据核验与受审正文闭环。

**反例：**新主题全部通过，点击继续问却进入ReflectionView，模型将传统条件升为个体事实并提前流出。或新AI上下文沿用旧profile.daily，把未审观察当事实来源。

**建议：**新入口只走ChatSession明确主题分支；不得把新报告/主题注入ReflectionSession。既有旁路可以在本轮记录为未修复，不能把本主题通过宣称全App已统一核验。新增出生generation保护应一并覆盖ReflectionSession，避免新资料生命周期只修一条路径。

**验收：**新主题出站请求没有旧personality/daily或关系他人資料；今日、关系、校时依旧明确标为旧路径未纳入新可靠性结论；报告→继续问路由实际到生产ChatSession。

## 在这一增量前应先处理的既有P2

### T-07 · P2：本命payload engineRevision只验证格式

依据：上轮 `review-implementation-technical.md:IMPL-01`，`NatalReadingReport.swift:NatalReadingInput.validate`，`NatalDossier.matches`。外层bundle摘要与内层metadata声明语义不同。

本轮AI衔接会把“版本有效”升级为授信条件，因此此项从可延后的本地报告健壮性问题变为本轮前置依赖。应从同一个bridge metadata取得预期payload revision并严格比较；合法64位hex但与metadata不同的payload必须拒绝。不能只把该值放进snapshot hash。

### T-08 · P2：native请求边界去掉了astronomy，却没有对natal对称去信任

依据：`AppStore.request` 首行只 `removeValue(forKey: "astronomy")`；匹配当前birth时会用仓库natal覆盖，但不匹配时不会覆盖调用方提供的natal。当前ChatSession执行器不允许模型直接传该字段，因此本评审没有证据将其定性为现有远程注入漏洞。

新handoff不可把携带的档案直接作为 `payload["natal"]`。建议在相同边界无条件移除调用方natal，仅允许仓库在验证当前主体后重新注入；需要他人资料的路径必须有明确独立计算入口。测试传入伪natal且birth不匹配时不得进入受信投影；保持正常relationship真实计算的兼容。

### T-09 · P2：局部可用性仍只有两份dossier隔离，不要作为主题新能力的默认保证

依据：上轮IMPL-02；八字与紫微共同验证，星宿/七政共享天文包。若新主题选择八字，可只验证主题实际依赖的八字字段，或者保留整包安全拒绝并准确报告恢复方式。不要为了避免紫微坏字段挡主题而放宽未知数据验证；共同身份错误必须整体拒绝。该项在有正常有效本命数据的小闭环中可延期，交付需说明当前限制。

## 草稿、失败与生产核验的可用性合同

- 主题点击只建立待发送上下文，不覆盖ChatView已有input，不自动停止working任务，也不自动发送。运行中可提示先等当前回答/返回册页；用户主动发送后才消费该意图。不能在send因working拒绝时提前清掉草稿。
- 网络/缺认证/核验拒绝/规则缺项分别映射恢复动作。离线报告继续可读；输入保存为原用户turn或独立待发草稿；重试使用相同主题与context，不重新起盘，不把失败fallback保存成“已通过主题文档”。
- 主题来源入口应关联到本次使用的依据及版本；返回不能只跳当前同名页而悄悄换主体。导航状态属于可用性，证据当前性属于信任，两个条件都要测试。
- 正文完成度不能以非空/HTTP200计数。真实验收应核查工具确实执行、目录来自真实输出、核验状态、主题回答是否回应所问、限制是否保留、存档是否能重建。

建议首批实测不超过8个用户轮次、一次完整路径最多固定上限的模型请求（预算由主代理记录后执行）：主题问题、两个连续追问、资料变更后重新发起、动态、模糊、事件边界、一次明确失败恢复。失败恢复可用可控网络断开或无权token验证运输失败，但最终至少一个成功请求必须走真实Supabase→DeepSeek→生产核验。不能用本地mock通过替代该成功链路；同样不能为了预算把真实失败标通过。
