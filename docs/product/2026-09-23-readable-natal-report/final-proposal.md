# 有时：易读本命报告与有依据的问道（修订稿）

版本 F1，2026-09-23。状态：已根据三个独立agent的28项意见修订；文档方案完成，未授权实施。事实依据见 [现状与证据](context-and-evidence.md)，逐项决定见 [评审采纳记录](review-decisions.md)。本文示例为界面/协议示意，不是对任何用户的断语，不使用参考截图中的个人资料。

## 1. 产品判断：值得做，但不能用“固定报告”包装未解决的解读问题

推荐方向是：**先让用户读懂自己的一个稳定册页，再按需看证据、看专业盘、问与自己有关的问题。** 默认易读报告放在“我的”，保留“今日”作为日历与日常陪伴入口。问道继续是对话入口；报告不是新的第五页签，也不替换全部首页。

现有本命缓存已经工作。真正缺的是：哪些解释有依据、如何把这些依据稳定交给下一轮对话、解释失败时怎样仍然给用户有用内容。上一轮32题只有2题完整通过，18题仍失败。不能因为生成一份固定长文就宣告这些缺陷消失。

对用户方向的五点修正：

1. “固定”应指输入、规则和版本明确时**可复现**，不指永恒正确的人格结论。错误规则必须可撤回，不能为了稳定继续展示。
2. 不默认同时写满性格、事业、财务风险、关系四大报告。先盘点已审定规则，再决定每主题能给什么；不把行业推荐、婚育年份、投资仓位伪装成已有能力。
3. 不能直接继承旧 `InsightEngine` 的性格称号、职业倾向。源码明确其为编辑启发式；改名“传统参考”并不能自动补足证据。
4. 不把所有体系揉成一个“你是什么人”。八字、紫微、天文与事件体系是并列证据视角，分歧应留下，默认也不自动全算一遍。
5. “更可读”不应变成一屏免责和缺项。MVP至少要给用户一段真正能理解且可核对的个人盘面解释，再提供现实处境追问；没有这个最低内容，就应继续补内容而不是上线空报告。

## 2. 目标、非目标与人群

**主要人群：**已有出生资料、对传统命理感兴趣但不熟悉术语的普通用户。想知道“这份盘说了什么、与我的困惑有什么关系、哪些不能据此判断”。

**次要人群：**会看部分盘面，想核对四柱、流派、取用和时间边界的人。专业层满足检查与探索，但不以专业工具大全定义主体验。

**本阶段目标：**减少看不懂、重复问、重新取数和解释被整段拒绝；让用户区分计算事实、传统解释和现实建议；支持有上下文的连续询问。

**非目标：**证明命理能预测人生；医学/投资决策；完整四体系所有事件断法；增加生肖评分；新增七政四余或星宿算法；社交配对、付费资源、云端自动长期画像；复制竞品的图表或“稀有天赋”机制。此次只交方案和评审，不实施。

## 3. 方案选择与最小价值

| 选项 | 好处 | 风险 | 决策 |
|---|---|---|---|
| 建档立即请求AI生成全本报告 | 看起来内容丰富 | 耗时/成本、泛化与错误固化；AI故障阻塞；缺规则也被长文填满 | 不选 |
| 纯专业盘加释义词典 | 低成本、字段可靠 | 用户仍不知道与自己有什么关系，回到“工具加聊天” | 只作为基础，不作为完整体验 |
| **程序生成可读基础报告 + 审定解释条目 + 按需AI咨询** | 稳定、离线可读、分层追问；可逐主题补覆盖 | 需做真实内容编辑和规则审核；初期覆盖有限 | 推荐 |
| 默认AI个性化改写全部固定文字 | 语气更自然 | 每次事实检查成本高，字面稳定性差，不能证明新增信息有依据 | 延后；不是MVP依赖 |

最小价值不是“你的日主是某字”。一个有效主题至少具备：一个个体盘面锚点、一句不扩张结论的解释、一个适用边界、一个可继续问的入口。例：“月令描述出生季节这层条件。它与日主的生克关系可单独查看，但不能只凭这一项定身强弱。”实际展示由当前字段和对应定义条目编译，而非复制这句给所有人。

对于性格/工作/关系象义，必须先建立传统来源和适用条件的条目；内容不到位时不发布该生活主题卡片。用户主动问到时保留支持的内容，准确说明缺项，并可选择聊现实处境；此状态不是该主题业务验收通过。

**修订后的发布门槛：**不以“字段+定义+免责声明”满足个人报告目标。先产出至少一条完整的普通人阅读路径：两个具有不同盘面条件的合成样稿和一个不适用反例；主文需要解释本盘几项信息如何关联、为什么采用这种传统解释，而非只替换干支。样稿必须来自已核对规则，不能在本次方案里先编结论，再要求实现追认。

目标产品仍是“易读基础解读”，不是把用户需求降格为纯读盘教育。若第一阶段只做到了定义与结构说明，可以作为内部“个人命盘导读”原型试读，**不能宣布用户要求的基础解读报告已完成**。面向用户以生活主题命名之前，至少一个生活主题须有完整经审解释单元、适用/不适用范围与差异样稿；本轮尚未交付这份内容库，这是明确实施依赖。其余主题按实际覆盖显示，不要求四大主题凑齐。

内容试读预设门槛（建议方案，尚未执行）：首轮招募6名非专业目标用户，不将它解释为统计代表样本；至少5人可在不提示术语的情况下复述一条本盘关系、一项不能推出的结论，并说明相较裸盘多理解了什么；不得出现把工程权重或传统解释当医学、收益/成功概率的未纠正误解。未达门槛先改内容再扩大界面。来源审核与理解度须分别通过，任一通过不能替代另一项。

## 4. 信息架构：四个现有页签中的一条连续路径

```text
今日（原有纸页/日历）
 └ 可选轻入口：回看我的册页（不自动刷新本命报告）
我的 → 我的册页（默认易读报告）
 ├ 基础概览 → 主题细读（结论与关键边界常显）
 │            ├ 一次展开盘面依据与来源 → 可选规则全文
 │            └ 带主题问道
 ├ 专业档案 → 八字 / 紫微 / 既有星宿与七政资料
 ├ 人生的节奏（明确选定时间）
 ├ 生活记录与关系 → 心情册页 / 关系里的我们（双方资料入口）
 └ 资料与设置 → 出生资料 / 校时 / 账号与导出
问道 → 倾诉 / 命理 / 起卦（沿用现有模式）
静心（保留）
```

“基础报告”不是永久入口名；推荐对用户称“我的册页”。具备完整生活主题前用“读懂你的命盘”，不先许诺“读懂自己”。专业入口称“查看专业档案”，不要让用户从“命盘手稿”猜与报告的关系。心情册页和双方关系入口留在我的同页分组，不塞进设置；本人的“关系主题”与“关系里的我们（双方）”明确区分。

## 5. 页面文字线框与交互

### 5.1 我的册页：读懂优先

```text
我的册页                             [设置]
出生资料 · 当前已确认                 [查看/修改]

先从这里读起
〈一段80–160汉字左右的目标篇幅；不是硬截断〉
说明本盘的1–2个已审定特点，必要条件随正文，不贴人格类型标签。
[为什么这样说]              [继续问这一点]

你的几个观察角度
  〈当前确有完整内容的条目〉   一句可核对的摘要     >
  〈已审生活主题，如适用〉     一句有条件的解释     >

[查看专业档案]    [人生的节奏：查看时间变化]
生活记录与关系：心情册页 / 关系里的我们（双方）
其他：校准出生时辰
```

这些长度是设计目标，需动态字体/可读性试验，不是当前实测。首屏不放四柱表、五行雷达、得分、证据ID、模型版本。导航由可发布内容生成：只有定义时称“读懂四柱/日主与出生季节”等准确条目；工作、关系、资源等生活标题须先有对应完整解释，不能用“待补充”卡片制造点击期待。没有这些主题不代表用户没有相关特质；范围说明放“当前可读内容”，不打覆盖分。状态如“基础内容已准备好；这一段解释未完成”只在实际部分失败时出现。

### 5.2 主题细读：一个解释单元，而非无限长文

```text
〈工作与做事方式〉
本次视角：八字                  [切换已支持视角]
〈当前状态与关键条件，例如“目前只能作为候选：仍缺……”〉
一句主要解释
1–3段短文：何种盘面 → 在此规则下怎样理解
这能说明：〈有限范围〉；还不能说明：〈最容易误推的一件事〉
“可以拿来观察”：开放问题，不把现实经历写成命盘事实

[展开：这段的盘面依据与来源]
  盘面依据：突出相关柱位/星位
  怎么解释：来源标题 + 当前适用条件
  [查看规则全文]

[结合我的情况聊聊]  [查看专业位置]
```

一般定义（例如十神是什么）与个人结论在视觉上区分。边界与结论同单元展示；规则长文、版本细节可以深入，关键“候选/未综合/虚岁”不可藏在第三层。若缺解释，只展示已支持事实及其释义，按钮改为“问这个盘面”，不暗示完整职业判断已准备好。

概览摘要也携带必要限定，不等进主题才纠正第一印象。“从当前主题找到对应依据”只需一次展开；规则全文可以再深入。首段是篇幅指导，不硬截字数、不要求大字号一屏塞完；术语首次出现就近给短释义，长定义按需展开。复制、分享、问道携带完整RenderUnit，不能只摘掉边界留好听的句子。

### 5.3 专业档案：让来源可以被看见

八字：四柱作为可点选纵列；选择日主后只高亮相关生克；藏干、十神、合冲逐项展开；有“以文字查看”。五行权重显示名称、计数方法和未综合条件，不作人格百分比。格局、扶抑、调候各自呈现，不合成唯一用神。

图解的最小价值是回答“哪两个位置、什么方向、只说明什么”，不只是染亮两根柱。选中时同屏呈现 `位置A/值 → 关系名 → 位置B/值`、程序生成的等价关系句与必要边界；窄屏改上下排列。每次只突出一组，其他关系按选择探索；图无额外认知价值时可以不放。相生相克方向及合冲效力由现有可信结果决定，图不补造规则。完整四柱保持独立入口，不靠反复横滑拼接两个屏幕外位置。

紫微：仅展示真实紫微引擎结果，点宫位看主辅星/亮度/四化与对应口径；虚岁标签固定在运限值旁。手机窄屏不强制十二宫小格，优先列表/可聚焦卡片。七政与星宿沿用独立资料入口，准确说明现有计算范围，不因为本次报告而增加解读承诺。

时间：从“人生的节奏”进入，先选大运/流年等范围，顶部持续显示选择；柱图如保留，只表达时间或有定义的计数，不表达运气高低。日历、时区、整岁/虚岁和精确交运时刻用系统格式化值，避免模型改写。

### 5.4 上下文问道

```text
问道 · 命理
[我的册页 › 工作主题 · 本命] [更换话题]
你想把哪段经历放进来一起看？
“最近在考虑换工作……”

回复：已核对的解释 + 对用户陈述的理解 + 需要的新信息
[依据：本命/当前流年，分别标识] [继续]
```

“更换话题”只解除当前焦点，不删除历史。用户键入“先不看命盘，只是想说说”时切换为倾诉并可见确认，不继续给每句情绪强配十神。用户问动态日期时更新范围提示，不暗中沿用旧“本命”标签。

范围不只存在顶部chip；每条回信保存并显示当时的“本人 / 体系 / 本命或具体时间范围”。“返回这段册页”与“更换话题”是不同动作。进入交接先呈现来源和可编辑问题，不自动唤起键盘遮住来源；用户点击编辑再聚焦输入。返回报告恢复滚动与原按钮焦点。

### 5.5 从册页进入问道，不丢原来的谈话

沿用当前单一聊天历史，不在MVP另造多会话管理。新增一个本地 `PendingReadingHandoff`：包含来源段落/报告版本、当前主体、阅读返回位置和可编辑的问题草稿。点击“问这一段”只准备交接，不自动发请求、不把浏览视为发送授权。

- 原问道为空：显示待发问题和来源条，用户编辑后发送。
- 原问道有未发送草稿：保留原草稿，进入前明确“保留原草稿，问这段内容”或“返回原草稿”；不得覆盖输入框。发送后可恢复原草稿。
- 正在生成回复：保留待交接，允许等待完成或由用户主动停止，再开始新回合；不在运行中替换证据。
- 新来源发送成功：在同一历史中插入可读主题分界，绑定这一轮及明确指代的连续追问；切换主题只解除焦点。
- 应用重开：已发送回合保留历史来源，未发送交接恢复为草稿提示；旧焦点不会自动约束下一次随意输入。用户可主动“继续这段”。
- 出生资料/报告版本变化：待交接失效提示并重新选择；不把旧段落悄悄重绑到新版本。每个来源条可返回原阅读位置（历史版则明确标历史）。

当前句明确的停止、改主题、主体变更高于旧报告上下文。只有“为什么/讲白话”等明确连续指代才沿用原焦点；不能把历史长文推测出的主题当成确定指代。

### 5.6 可访问性与有时的视觉约束

本节是后续验收规格，**不是本轮已通过的测试**。沿用SujiTheme纸面/墨色/青瓷、宋体标题和系统正文；长报告在不透明纸面上阅读，以分隔和留白组织，避免堆叠玻璃卡/来源徽章。概览只承载阅读起点，长文在主题页；心情/关系入口不需要读完报告才到达。没有依据的分数、稀有度和浮夸人格印章不进入设计。

- **VoiceOver：**报告/主题使用原生标题语义；RenderUnit按“具体条件→解释→动作”读取。按钮可访问名称包含对象，如“继续询问：日主与月令的关系”。展开依据聚焦其标题，关闭回到原触发按钮。进入问道先读可见范围摘要，再进入输入；只播报一次局部完成/失败，不抢走正在阅读的焦点。更新/撤回后焦点留在同主题的状态说明，不能掉回页首或隐藏图中。
- **最大辅助字号/窄屏：**主题按“标题→摘要→完整状态→动作”纵排；不缩小字体或截断关键状态。动作纵排且可换行，目标至少44×44pt。上下文摘要可换行，不为键盘挤掉时间/主体；正文可滚动到所有操作，不以sticky大面板遮住内容。
- **弱视与颜色：**最终实际组合测普通文本至少4.5:1，大文本及必要图形/控件至少3:1；覆盖深浅色/青瓷/增加对比度/减少透明度。现有token不自动意味着新组合达标。必要限定不是极淡小字，不只靠颜色区分候选/失败/选中。
- **图文等价：**图、文字、读屏引用同一值和方向；选中有文字/形状，不靠红绿。完整四柱/紫微宫位有纵向列表；多体系分歧在窄屏与大字号下按方法顺序展示，不硬做两列。
- **动效：**保留今日纸页仪式；报告无强制揭页/长文打字机。Reduce Motion用直接状态切换，取消自动镜头位移/连线生长；动效不承载唯一的关系或错误信息。

必须用VoiceOver实际完成：读一段及边界→展开依据→返回原位→带主题进入问道→遇局部失败→回到同段。自动identifier检查不能替代这条流程；本轮旧截图与旧QA均不向新界面继承“通过”。

## 6. 完整流程与失败路径

### 6.1 首次登录、建档与报告

1. 按现有方式登录并恢复账号；明确出生资料用于排盘，聊天仅在主动使用AI时发送所需片段。
2. 确认公历、北京时间、性别规则参数、城市/经度；未知时辰不能暗设12点。MVP新增已登录但未建个人盘的正式状态：可选“稍后填写/我不确定时刻”，继续今日、静心和普通倾诉，个人命理入口只说明缺少何项。重开应用也不再次全屏强制填表。自动全球时区与无时辰排盘另立项目，不能把示例日期当用户资料。
3. 本地生成本命缓存 → 验证契约 → 编译基础报告；各阶段分别记录，不让AI联网失败影响本地报告。
4. 成功后提示“册页已准备好”，进入易读概览，可返回今日；不强制读完或问一题。
5. 本地排盘失败：保留填写资料，显示明确失败阶段及重试；允许进入今日/静心/普通倾诉，命理入口显示待完成，不全局锁死。若已有旧档案，不能当新档案继续回答。这是对现有全局gate的拟议改变：登录要求保留，个人报告要求资料，但非命理功能不要求完成排盘。

### 6.2 回访

启动先加载有效本地报告，稳定呈现，不因日历日期改变重写本命。动态节奏卡另查时间证据；旧日期明示。无需自动发模型请求。云端只恢复出生资料时，本地重建报告，提示“基础册页已恢复；此设备没有旧咨询记录”，不承诺全部恢复。

### 6.3 修改出生资料或口径

编辑前列出会重算的主题。保存使用 draft → compute → validate → promote；计算中旧版可读但标“根据旧资料”，暂不作为当前咨询证据。新版本成功后原子切换活动指针，保留有限上一版本供解释差异/撤销。失败保留用户输入草稿并允许返回旧资料，不出现“新出生资料配旧报告”。

用户可见状态固定为“待生效资料 / 当前生效资料 / 历史资料”。用户已更正旧生日时，重算失败不能自动恢复旧资料为正确版本。给三个动作：“继续修改”“重试建立”“只回看旧报告”；旧版持续显示“仅供回看”，当前咨询入口不可用旧版取证。只有用户明确“撤销这次修改、恢复原资料”才恢复活动版本。成功切换后只说明资料/计算差异，不说用户性格变了。

不能只在长页顶部放提示。旧版本标记和“本段仅供回看，不能用于当前咨询”在受影响主题原位出现；被撤回的段落保留占位：“这段解释的依据已修订，原结论已撤回”，可查看修订原因，不静默消失。有效独立单元仍保留，重试不跳回页首。撤销修改恢复旧活动版本时明确说明草稿的去留，允许先保留草稿供继续编辑。

打开旧聊天时，“解释当时这句话”使用历史版本及其当时依据，并标历史；若依据已被撤回则只解释为何不再采用。“按当前资料重新问”创建新回合与新绑定。两者不能通过同一个无说明的“为什么”按钮混为一谈。

规则/引擎升级按依赖重算；一般旧版可历史读，已知错误断言直接撤回并解释“此段依据已修订”。变化说明区分：资料改变、算法修正、规则口径调整、纯措辞更新。切换流派不是用户无意中触发的主题开关。

事务不能只更新一个报告指针。拟议本地提交在**同一事务**更新已确认的 `subjectRevision`、出生资料、快照引用、manifest、active pointer与待同步outbox记录；草稿始终另存。每次编辑/计算使用不可复用的 `operationGeneration`，A→B→A也不会接受第一轮A的晚到结果。事务提交成功后才允许发送网络请求，不能先promote再另写outbox而留下崩溃丢同步窗口；网络失败保留本地完整版本与待传revision，不退回混合状态。outbox在现有出生同步边界内演进，不能假设当前Supabase已支持多设备revision并发合并；如需服务端compare-and-set/schema变化，应另列实施和部署变更，不在本轮执行。

崩溃恢复要求：每个持久化点后重启只能读到完整A或完整B，或明确未激活的草稿。资料更正待计算期间冻结新的个人命理咨询，允许非命理功能；旧报告只回看。与现有 `AppStore.updateBirth` 先保存再计算的实现不同，这是MVP必须改造并测试的边界。

### 6.4 追问、动态与事件

静态“为什么/讲白话”使用当前断言/证据绑定，不重排盘，不把旧AI正文当来源。问“今年换工作”需要流年范围与真实工作处境；程序先解决时间，AI再解释限定，不自动回答成败。关系问题没有对方信息先澄清范围：只谈自己的关系主题，还是录入双方资料；绝不假设对方盘。

六爻/奇门是独立事件会话：用户明确选择/确认问题、主体、时间/起局方式等已有条件后执行；重试复用同一事件盘，重新起局需显式新动作。普通“今天适不适合拆卡”仅命理咨询，不等同起卦授权。

### 6.5 离线、未登录与失败

| 状态 | 保留什么 | 可以做什么 / 不说什么 |
|---|---|---|
| 已登录缓存会话、当前离线 | 已验证本命报告、基础解释、专业盘、本地历史 | 浏览、查看依据；AI入口说明待联网，不静默发送排队问题 |
| 首次未登录或明确退出账号 | 公共使用说明；不展露前账号报告 | 按现有账号入口登录；不把账号隔离放松为离线匿名读取 |
| 网络/服务不可达 | 已有报告和本次本地取得的事实 | “连接未完成，已保留本次资料”；重试AI，不重复起盘 |
| 本次未计划/未取得需要的证据 | 已有可靠报告，追踪缺少哪项 | 有明确需求则最多补一次取数；仍失败说明阶段，不说全部命盘不存在 |
| 工具失败/结果契约不合格 | 无关有效章节 | 局部失败与重试；不把error JSON当正常事实 |
| 能力未覆盖 | 支持的盘面与解释 | 说明此事件/判断尚未支持；不以“再试一次”诱导无效付费重试 |
| 文本核验拒绝 | 已验证部分 + 简短核验状态 | 撤掉对应解释块，保留可靠章节；不改成“尚未取数” |
| 账号切换/资料变更中异步返回 | 当前账号/资料状态 | 丢弃过时响应，不污染新档案；可审计取消原因 |

对用户不显示 `核验拒绝`、`契约失败` 等内部术语作为主文案。每个失败块保留原问题，说明“已回答哪部分/哪部分未完成”。例如解释修复耗尽：“这次解释没有完成，你的命盘与已有说明都已保留”；主动作“查看已有说明”，可选重新尝试本段。无输入定位填写；计算失败可重算；网络失败可重新连接；模块缺项没有无效重试；配额耗尽显示已知恢复条件与离线可读入口。内部阶段码只进诊断。

## 7. 数据分层与契约（拟议，非已实现接口）

基础原则：**facts 描述算出了什么；assertions 描述何种规则在何条件下适用；rendered sections 描述怎样给人读。** 用户说的经历是第四类上下文，不能回写为命盘事实。

| 实体 | 必需字段 | 生命周期 / 信任 |
|---|---|---|
| `SubjectProfileRevision` | ownerScope、subjectID、revisionID、birth字段、输入时区语义、地理/性别参数、confirmedAt | 自己/他人分开；不能用姓名做ID；历史版本不可变 |
| `CalculationPolicy` | policyID/version、历法边界、太阳时适用范围、日界、年龄口径、体系方法 | 根据真实引擎能力固定；不是随意配置UI |
| `NatalFactSnapshot` | snapshotID、subjectRevision、policyID、engineRevision/schema、payloadDigest、createdAt、typed facts | 本地可信引擎产物；输入未变可复用；不包含 personality 文字 |
| `RuleDefinition` | ruleID/version、原始来源定位、所采口径、前提、反例/冲突、所需字段、允许输出与限定 | 人审内容库；来源存在不等于适用已证明；编辑类另标 |
| `RuleAssertion` | assertionID、ruleID/version、snapshot/field refs、evaluated preconditions、status、mandatory qualifications、scope | 状态 supported/conditional/conflicted/notCovered；冲突不择优美化 |
| `ReportSectionRevision` | sectionID、revisionID、topic、assertion refs、renderer/template version、body/digest、status | 程序编译或经批准模型产物；report != evidence |
| `ReportManifest` | reportID、subjectRevision、section revision refs、language、versions、status、active pointer | ready/partial/stale/withdrawn/rebuilding；局部发布、原子切换 |
| `TimeEvidenceSnapshot` | subject refs、system、selectedRange、UTC边界与展示时区、ageConvention、算法/规则版本 | 可预算但不能当永久人格；保留查询范围，不以createdAt代替有效性 |
| `EventCase` / `EventEvidence` | eventID、参与主体、用户确认的问题、inputs、castID/seed/receipt、referenceInstant、policy、validity条件 | 一事一档；重试不改盘；变事件不复用旧结果 |
| `ConversationEvidenceBinding` | turnID、subject/scope、原始snapshot/assertions、materialized receipt refs、validity decision、versions | 每轮程序签发的本地绑定；不是模型声明的有效性 |
| `UserContext` | 原文/经确认摘要、来源turnID、适用主题、可撤销标记 | 用户自述与AI假设分开；不推断敏感画像写回档案 |

上述是逻辑实体，不要求MVP把每一行都建成数据库表或泛型引用服务。MVP只允许“本人”获得新报告证据权限。多主体字段先作为拒绝/隔离边界；用户提到姐姐、对象或双方分析时进入专门澄清/既有明确双方入口，不用本人binding兜底。同生日可以复用数学计算，但绝不能复用subject身份、角色、授权或自述。未来关系契约必须含参与角色及每人revision，不能只比birthFingerprint。

ID建议采用账号私有命名空间内随机稳定ID，版本/指纹用于本地匹配与去重；不要把可枚举生日明文或无盐生日hash当公开身份。所有事实引用同时保存字段JSON Pointer与规范化值摘要；不存在字段一律拒绝，不让模型构造指针后自证。

示意（ID为新协议占位，不是已有引擎字段）：

```json
{
  "assertionID": "asrt_local_001",
  "scope": {"kind": "natal", "subjectRevisionID": "subject_revision_synthetic"},
  "rule": {"id": "proposed.day-master-definition", "version": "1"},
  "facts": [{"snapshotID": "snapshot_synthetic", "pointer": "/bazi/pillars/day/ganZhi/gan", "digest": "<canonical-value-digest>"}],
  "status": "supported",
  "qualification": "definition-not-personality-test",
  "allowedRendering": "audited-template",
  "dependencies": ["birth", "bazi-calendar-policy", "engine-revision"]
}
```

实际 natal payload 与 get_domain 结构不完全相同，需专门 adapter；上述 `/bazi/...` 是现有工具输出惯用路径示意，不可直接假设缓存有同层路径。

## 8. AI在哪里发挥作用，哪里不该交给它

### 8.1 基础报告生成策略

MVP在本地建档后按需编译首个基础报告，随后缓存；内容来源是受审规则条目和类型化字段。没有AI就能读最基本的个人盘面解释。预生成所有可能主题既浪费又制造无依据内容，所以只生成有完整依赖的章节。

AI用于理解自然语言、把问题与主题连接、整理用户明确自述、选择/排序已有解释、提出澄清、请求额外支持的工具。MVP按第8.4节的闭合动作协议交付命理内容；更自由的综合属于待验收后续范围。基础报告后续如允许AI改写，保存模型、实际返回model、prompt/schema、内容版本和核验记录；原稿仍可回放，不能无声覆盖固定版本。

### 8.2 一次咨询的编排

```text
输入 + 显式主题绑定 + 用户处境
 → 路由（静态/动态/事件/他人/倾诉/模糊）
 → 能力与输入检查（缺条件则澄清；缺实现则说明）
 → 可信证据准备（MVP：本地仓库校验 + 现有工具缓存投影）
    读取可信本地快照 → 检查依赖 → 确定解释直接渲染
    需模型或新范围 → 执行本轮真实工具投影 → 验证输出/持久化
 → ContextPackage（有限相关事实+规则+限定+用户自述）
 → 程序解释块 + AI选择/场景讨论
 → 结构/绑定/字段/范围/语义核验
 → 独立章节接受或拒绝 → 原生展示与归档
```

**评审后收缩：通用EvidenceBroker不作为MVP前提。** 现有 `ReadingVerifier.verify` 没有binding参数，把一份新JSON放旁边无法让它验证历史证据。MVP分两条静态路径：

1. 已审报告块的“讲白话/解释依据”，由本地可信仓库重新确认版本、前提与依赖后，直接渲染对应完整解释单元；可以零模型、零新工具。保留“本次从有效本命复用”的日志，不冒充重新计算。
2. 确需进入现有模型问答时，由程序直接执行当前本地工具（如 `get_domain`）进行**本轮可信投影**，利用 `AppStore.request` 的本命缓存；这是轻量读取/投影，不重新排本命，也不让planner决定是否漏取数。它自然产生当前ToolContext的真实回执，仍走现有校验。旧回执context绝不改写。

未来Broker如要跨回合直接授信，必须先升级协议：只有本地可信仓库/执行器可构造不可从外部Codable直接实例化的 `VerifiedEvidence`；包含原计算来源、owner/subjectRevision、policy/版本、撤回检查、投影执行ID与字段映射。验证入口消费此对象后才生成模型消息。保存的binding仅是待验证记录，`validityDecision=true`不是权限。账户、主体、规则、字段、来源任一不符，须在请求发出前拒绝。时间/事件仍使用各自有效性，不能删除全局context校验来达成复用。

“进入现有模型问答”只复用客户端、真实工具执行与核验基础，**不允许报告交接及连续追问静默回退到旧自由writer+verifier路径**。这些回合只接受闭合解释/追问动作协议；不支持就澄清或给能力边界模板。旧自由路径在开发阶段可保留用于对照和读取历史，但不能作为新报告的兜底。正式发布前，普通问道的命理入口也须按同一能力注册表路由，未通过业务验收的自由命理输出不得作为默认通路继续暴露；倾诉与现有六爻/奇门来源约束路径分别维持自己的清楚边界。

路由优先级：当前句明确的停止/改主题/主体变化与本次明确体系选择 → 本次用户确认的事件/时间条件 → 尚有效且确有连续指代的报告焦点 → 历史摘要作为非证据背景。存在多个互斥当前意图先澄清。报告主题不得压过“不要继续看这个，换工作话题”。模糊“帮我看看”在无主题入口时正常澄清；有明确主题来源的“为什么”可先解释，不强迫用户重复信息。

### 8.3 上下文包

包含：requestID/turnID、subjectRevision、scope、selectedDate/range、展示时区及年龄口径、可用能力目录、最多与主题相关的fact/claim、不得去掉的限定、绑定和版本、用户自述（明确标来源）、不确定项。排除：全量档案、无关他人资料、旧失败草稿、用户照片、未确认的AI记忆。统一出站构造器控制planner、writer、review、repair的最终HTTP消息；只裁facts而继续携带最近20条原文不算最小化。原始当前问题按用户主动发送保留；历史按主题、主体与确认的用途选取，不由自由摘要重新引入已撤销自述。每一阶段都应能检查实际出站载荷。

事实/断言ID由程序列出，模型只能引用白名单。字段值和日期通过程序模板注入。真正自由语言的“这说明你一定很适合管理”即使带正确ID，也可能无依据；不能因为source ID存在就接受。

### 8.4 核验与有限修复

分三类输出协议：

1. **确定字段/已审解释块**：程序格式化事实，或模型选择完整claimID，程序渲染；限定与正文不可拆。已有 `BaziFrameworkReading` 可作为模式，不照搬为全体系已完成。
2. **命理里的处境追问**：MVP只允许明确动作协议，如引用用户原文span、选择已审开放问题、询问缺少的条件；不得用自由连接句扩张盘面结论，也不能把模型猜测写成用户经历。结构示例为 `claimSelection[] + questionActionID + quotedUserSpan?`，程序负责正文。用户明确选择自由倾诉时另开可见模式，不注入盘面依据；倾诉本身仍是AI输出，不标为已经过命理证据认证的结论。
3. **澄清/边界答复**：能力注册表与输入缺项驱动的短句模板，不要求伪造工具成功；禁止顺带夹带个人预测。

检查包括：主体与账号、版本/时点、字段值、规则状态、日期/年龄单位、来源定位和有限可执行的语义约束。不承诺已有通用中文蕴含证明器。模型review仍是辅助，不是数学证明；不能把无法验证的命理推断改名“场景讨论”继续展示。完整自由命理综合留到后续，经明确反例/人工语义门槛验证后再评估；正文ID合法不足以证明推论正确。

MVP以共享 `UserActionBudget` 限制整个动作，不能每块套一次旧verifier。建议上限为**5次模型尝试**：规划1、写作/选择1、review1、修复1、复核1；确定路由可省规划，确定解释无需模型review。无效协议、网络失败、取消后的已发请求都消耗预算，额外review不能突破总额。一次缺证据补取指一次受原工具allowlist/maxCalls约束的本地工具批次，不额外打开新的模型循环；全回合共享既有工具次数上限。建议客户端总动作截止120秒，服从已有单请求90秒上限，余时不足时取消/返回已有内容；这两项是待测产品上限，不是实测延迟承诺。

5次与120秒上限均属于一个 `actionID`，不是每个阶段或分块。发送前持久化actionID与attempt预留，自动恢复/继续沿用同一action的剩余计数和原截止时间，崩溃重启不重置。预算耗尽主动作是查看已完成内容；用户显式“再次尝试这次解释”创建新的actionID并保存 `retryOfActionID`，旧action计数永久保留。新动作仍关联原问题、冻结范围、同castID及Supabase日配额，不重新起盘、不自动无限续开。配额是次数保护，不是精确计费证明。预算不足绝不跳过核验。

### 8.5 静态、动态、事件有效性

| 类型 | 复用条件 | 不应复用的反例 |
|---|---|---|
| 本命事实 | 同owner/subject/birth/policy/engine/schema；本地可信来源 | 修改时辰或引擎修正后只检查姓名相同 |
| 本命规则断言 | 上述+rule版本/前提/冲突状态仍有效 | 旧用神解释在新规则撤回后仍标当前结论 |
| 流年/大运 | 同主体/体系/范围/时区/年龄口径/版本 | 把去年报告解释为今年；以相同公历年覆盖节气边界 |
| 今日上下文 | 同问题参考时刻语义、明确日期范围和日界 | 午夜后“今天”自动复用昨日；原重试却换成今天重算 |
| 事件盘 | 同eventID/确认输入/castID与版本；返回历史解释注明当时条件 | 把求职盘用于收款；把同一事件重试变成重新随机起卦 |
| 对方/关系 | 明确双方subjectRevision及对应规则输入 | 用本人夫妻宫冒充对方星位或合盘 |

有效范围不等于简单 TTL。本命可跨时间复用，但规则可能撤回；历史事件盘可以长久回看，却不能用于新事件成败判断。绝对日期、相对“今年/今天”、年龄必须在数据层区分。

### 8.6 日期、年龄与引用不是让AI自由换算的文字

拟议 `TemporalValue` 至少包含 instantUTC、displayTimeZone、calendarBoundaryPolicy、selectedRange、referenceSemantics（绝对日期/本次今天/事件当时），`AgeValue` 至少包含 value或range、convention（整岁/虚岁/交运换算参考）、对应时刻与算法版本。对模型发送可引用的valueID，用户看到的日期/年龄由程序格式化；限定单位与值不可分离。模型若自由新增“明天交节气”“35岁开始”等时间句，则视为新增需校验的断言，不能因为相邻有日期ID就放行。

结构化输出块必须显式依赖所有相关claim、时间值和限定块。删除一个未通过块后，要重新验证剩余块的指代与依赖闭包：不能留下“所以适合辞职”而删掉其前提，也不能删除“只是候选”而保留结论。无法切开的综合段整体拒绝；其旁边独立的程序事实块仍可保留。

每个 `RenderUnit` 是不可分割的结论、条件、时间/年龄口径和必要边界；状态沿明确的依赖DAG传播，循环引用直接不接受。撤回A时所有依赖A的B/C一起撤下，独立D可保留。MVP不允许自由跨段“所以/上述”形成未声明依赖。复制、分享、VoiceOver和历史都用同一验收后的单元，不能在扁平化时丢限定。

格式化还不能保证“选对时间”。拟议 `TemporalQuery` 保存原文span、absolute/relative/backReference类型、冻结referenceInstant、解析来源、区间闭开语义、所选体系与解析/确认状态；之后分别生成八字立春年、紫微历法年等范围，不共用含糊的year整数。“我35岁那年”必须确定周岁/虚岁及对应范围；“去年那次”必须确定回指。跨午夜重试保留原查询，新提问再解析，歧义正常澄清。

### 8.7 版本命名与撤回传播

不要把当前两处 `engineRevision` 当同一值：`AppStore` 使用加载脚本的digest，工具metadata有引擎声明revision，迁移需实测并明确映射。新manifest区分 `engineBundleDigest`、`engineDeclaredRevision`、schema、calendarPolicy、ruleCatalog、ruleEvaluator、projectionAdapter、semanticTemplate、layoutVersion、prompt、verifierProtocol，以及请求固定模型名/实际返回model。确定报告的模型字段为空，不伪填“AI生成”。

缓存有效性按依赖逐项返回失效原因；Swift规则变更即使JS不变也会使相关assertion失效。语义措辞改变必须重新审核，只有纯布局可不重评。MVP撤回清单随应用规则包发布，每次激活和新咨询前检查；离线只知道本机已取得的版本，不能保证旧App即时得知撤回。远程紧急撤回/规则包分发是另一个待评估协议，不能假装当前Supabase已有此服务。

## 9. 同一条真实产品链路的示例（非预测输出）

| 步骤 | 用户 | 程序与AI如何做 | 交付/边界 |
|---|---|---|---|
| 基础 | “四柱和日主是什么意思？” | 使用当前本命快照和已审定义；字段由程序填，不请求模型重算 | 展示四柱位置与日主的定义，允许点柱；不是性格判定。对应矩阵02/09错误字段风险 |
| 追问 | 从此段点问：“那日主和月令什么关系？” | 根据已验证主题来源取已有月令字段/生克定义；确定解释可本地渲染，模型路径执行缓存投影获取当前真实回执 | 解释实际关系和不能单凭此项定强弱；记录 reusedNatal，不把零新排盘误判无证据 |
| 动态 | “那今年换工作呢？” | 不延伸为静态人格；取当前明确流年/运限，程序格式化北京时间和年龄；使用审定动作询问考虑的变化 | 已支持时间事实+有边界的处境追问；没有成败规则则说明，不能输出必成/必败；自由倾诉另行明确切换 |
| 事件 | “用六爻看看这次面试能成吗？” | 进入现有确认流程，生成新的eventID；确认后才起卦；保留原参考时刻 | 条件与候选并列；未化解竞争不能定成败。奇门同理，角色取用未定就明确缺项 |
| 模糊/跨话题 | “算了，帮我看看呗” | 当前指代与退意不明，询问是继续此事还是换主题；不自起新盘 | 正常澄清；报告仍可读，不显示计算失败 |
| 特殊 | “几岁能有孩子？” | 本命子女对应可复用，但生育年龄规则未实现；边界无需依赖AI发挥 | 保留子女宫等可靠解释，说明无法据现有模块判断具体年龄或医学能力，询问是否看相关主题 |
| 今日 | “今天适合拆宝可梦卡吗？” | 需要时取今日历法；不转六爻，不把日干支转概率 | 说明目前无拆卡宜忌/出卡概率规则；可聊预算与娱乐期待，后者不归因于命盘 |

如用户没有明确选择传统视角，可以先讨论现实问题；不能为了“显得会算”强行取全部体系。

**MVP与后续的区别：**基础解释、静态追问、澄清及所有范围转换的正确识别属于MVP。动态问题至少显示/确认年份、调用已有可验证的强类型时间事实或准确说明能力缺项，不能继续用旧本命回答。今年/去年/对方/事件/转倾诉的边界处理不能推迟到P2。表中的完整流年综合与最终事件判断仅在相应内容能力通过验收后开放；现有事件入口可保留其真实可用范围，不因新报告而承诺已补齐。

## 10. 内容库、多体系分歧与个性化

先做“可发布解释目录”清点，每条记录 source（可追溯书目/章节/对应工程规则）、解释口径、输入前提、传统/工程/编辑性质、反例、允许用语、不能推出什么。不能新造古籍引用；缺来源的条目标未审，不进入基础个人结论。实现者、规则核对者、文案核对者分别签记录；源码自带文案不等于已审。

MVP优先：四柱和十神定义；日主/月令关系；扶抑权重与局限；格局候选/调候与扶抑的区别；紫微宫位与星位的基础说明。性格/事业/关系条目是否发布取决于逐条通过，不以模板数凑齐覆盖。

多体系有冲突时展示“观察角度不同”的两列或顺序段，每项都标用途/前提；如果其实是事实冲突（同柱出现两值、同主体版本混用），应阻断并修复，而非称流派多元。不得投票、平均、选更悦耳一句，或合成全人分数。

个性化来自用户愿意说的经历、阅读深度与关注主题；稳定的事实层不随对话漂移。AI生成的“你是内向者”不能写回永久档案。用户可纠正“这不像我”，记录反馈为自述，不调整出生时间来迎合。任何长期记忆独立授权、可查看/删改；不在MVP默认积累敏感画像。

## 11. 适配现有技术，而非另造一套产品

| 层 | 适配方案 | 明确新增工作 |
|---|---|---|
| 本地 JS Engine | 复用 natal/既有工具和天文模块；输出adapter把personality排除出facts；不重写算法 | 契约投影与policy版本登记；必要的规则来源目录 |
| Swift Core | 基于 NatalDossier、ReadingDocument、闭合断言做 ReportCompiler 与可信本地投影；通用Broker延后 | 单主体实体、依赖验证、TemporalQuery/强类型值、RenderUnit、统一预算 |
| SwiftData / AppStore | 沿用account SavedState范围与scopeRevision；report以独立key/blob加schema | 事务式active pointer、局部失效、版本保留/撤回、迁移 |
| SwiftUI | 我的册页/主题/依据层；复用现有专业图和问道；纸墨tokens | 新阅读层级、显式上下文chip、无障碍等价呈现 |
| Supabase → DeepSeek | 沿用Auth、配额、固定代理；只发相关上下文 | 客户端协议/预算/诊断适配；是否需要服务器schema校验待实施评估，不预设已部署 |

设备负责出生资料处理、可靠计算、报告编译、有效性和展示；服务端目前负责认证/限额/推理转发，不是假定的“可信命盘数据库”。将来如需多设备全文同步，需另设计权限、加密、冲突与删除，不作为此次前置。

### 11.1 迁移、缓存与回放

- 现有聊天保持原文和已保存文档；不把历史AI文字补写成新assertion。新回合按新协议执行，旧回合标为历史版本。
- 从旧NatalDossier通过可信adapter重建facts/报告，缓存可重建但不要清空日记/对话。对比出生fingerprint与scopeRevision后再激活。
- 本地回放使用当时manifest、模板和证据快照；当前查看时另给“历史/已修订”标记，不偷偷用新规则改旧话。
- 外部Archive导入继续去掉可信证据权限；可保存可读历史文字，新个人报告必须经本地引擎重算。payloadDigest不是签名。
- 规则升级只重新编译依赖章节；算法版本覆盖较粗时宁可整盘重建，不声称已有精细增量依赖。纯排版/措辞变更不必重算引擎。
- 暂存中断、崩溃、低存储要保持活动版本完整；旧版保留有上限，按账号清理，不能清到未上传的用户记录。

新归档必须有独立、版本化的导出DTO白名单：用户记录与只读呈现可导入，活动指针、可信binding、assertion授信与operation状态不导入。外部导入API与本地恢复API分离，不能让通用JSONDecoder决定信任。现有20MB总归档上限先保留；新引用图需限制节点数/深度并拒绝循环、悬空、未知版本，具体容量用现有最大档案测定后写入schema，不无限放宽。

历史依据按可达引用保留；若因用户删除或容量清理移除快照，历史降级为“仅保留文字，原依据已不可回看”，不能保留假的可点依据。删除墓碑不能被旧备份重新激活，重新导入内容只作历史记录。MVP不做跨设备完整报告/聊天同步；登录恢复出生后重建基础报告，不承诺恢复原AI措辞。

### 11.2 全入口迁移清单

| 入口 | 当前实现 | 本方案过渡策略 |
|---|---|---|
| 我的旧PersonalitySection | 直接读取personality和日柱文字 | 新报告不得沿用其权威；替换为已审单元，旧值不进入facts |
| 问道命理/起卦 | ChatSession工具、核验、结构化专门路径 | 报告交接与连续追问不得回退旧自由文稿；正式发布前普通命理入口也按统一能力注册表收敛；旧代码只作历史/对照，不以失败路径充当新报告兜底 |
| 今日反思 | `SujiApp`传profile.daily，ReflectionSession直接流式 | 保留日签/用户记录的反思；过渡期不注入未审personalObservation，需要盘面时显式转命理管线 |
| 关系里的练习 | `ObservationViews`传relationship result.json | 现实关系讨论只传用户选择的自述；涉及盘面解释须转双方明确输入及统一管线，不能自由推断对方人格 |
| 校时的整理 | ReflectionSession接多候选资料 | 可整理用户回忆，不以AI证明某时辰正确；候选盘解释必须隔离revision并走审定单元，未迁移前不纳入报告可靠性声明 |
| 月度回望等记录反思 | 须在实施时枚举全部ReflectionView调用点 | 按实际输入区分记录总结和盘面推断；发现任何盘面旁路都先隔离再纳入验收 |

这不要求关闭所有自由倾诉，但要求所有命理资料入口具有同样的证据边界。现有ReflectionSession已有账号/出生隔离，不能误称完全无保护；缺的是命理内容闭环。任何未核验命理草稿不先流式当正式结论显示，旧历史仍可读并标历史。

### 11.3 隐私与账号隔离

沿用当前账号范围，退出后隐藏个人报告；清除/导出行为与既有数据政策一致。AI仅收到必要的脱标识事实与相关自述，subjectID在服务端请求中使用会话内别名；未必要发送原始完整生日与城市。模型可从事实推断部分资料，不能承诺完全匿名。

他人资料需用户明确选择提供，标识本人与对方，不在普通问题中自动发送所有关系档案。生产日志记录阶段/状态/字节/耗时/版本，默认不记录原文、生辰和payload；带真实内容的诊断需独立同意且可撤回。测试用合成档案，不挪用截图数据或真实用户历史。

只给ContextPackage脱标识不够：验收必须捕获planner/writer/review/repair最终请求，用合成敏感标记证明无关历史及他人资料不外发。撤销自述后，后续请求也不能从旧assistant总结或历史缓存恢复它。原始文字本地历史保留与继续作为模型输入是两种权限，须分开。服务端不记录原文是当前函数行为，不等同第三方推理服务的长期隐私政策已由本方案验证。

## 12. 成本、token与延迟：先设预算方法，再测量

本方案没有新跑模型，没有实测新架构延迟/价格。现有请求上限和配额见现状文档，不将435次历史调用等同未来成本。

按用户动作记录 `Nplanner + Nwriter + Nreview + Nrepair`，各请求输入/输出token、是否缓存计费、失败次数。费用估计用部署时官方对应单价乘实际usage，拿不到usage时只能给估算且注明误差。不要用中文字符数冒充token。

- 打开/回看基础报告：目标0次模型请求；本地编译耗时与缓存命中分别测量。
- 审定定义追问：可走零模型确定回答；自然语义无法确定才路由，不为词典答案强制调用review。
- 新动态/场景咨询：通过统一预算限制总请求及输出长度；优先主题投影，避免每轮塞全部盘。
- 达配额/超时后保留本地报告与已验证内容，显示恢复条件，不能无声自动重试。
- 记录点击到基础可读、点击到首段完整可读、整轮结束三个时间；流式未经核验文稿不先当正式结论展示。p50/p95在后续真实受控验收测，不在方案中编数。
- 目标阈值按现有机型基线与用户试读确定；成本表按“新建档/日回访/静态追问/动态/事件”分别估算月量，不用平均问题掩盖重试开销。

预算公式：每动作模型费用估算 = Σ(各阶段实际输入token×当期输入单价 + 输出token×输出单价)，有缓存计费时单列；月量估算按动作类型的发生量乘实测分布，再单列失败/手动重试。现有工具最多5轮规划、8次工具以及旧verifier最多5次模型请求，会叠加；因此5次新动作总上限需要实际统一调度改造，**不是改一个常量就已经生效**。不得按章节乘开独立预算。各阶段request/byte/token/latency/decision原因分开记录，不输出原文到常规诊断。

## 13. 验收：分别衡量可用性、依据正确性和体验

不设“预测准确率”指标。核心指标：用户能否复述主要意思与边界；报告有效命中率；需要证据的问题取得正确证据比例；静态复用正确率；澄清恰当率；有事实却误报无计算比例；核验假接受/误拒；未支持判断被正确说明；每轮费用/延迟；跨账号或跨事件错用为阻断级错误。

以下为后续实施验收要求，不是本轮已执行测试：

| 用例 | 合理预期 / 反例 |
|---|---|
| 相同资料多次打开册页 | 同版本同内容；零AI；不能随机性格变更 |
| 只有日主/月令字段+定义 | 正确解释关系；不能由一个字段判所有人格 |
| 资料改时辰，重算失败/中断 | 草稿与旧报告隔离；不出现新资料旧结论；可恢复 |
| 更新一条已知错误规则 | 受影响块撤回，其他块可读；历史明确旧版 |
| 静态追问跨午夜 | 可复用同一有效本命；不同今日证据必须分别验证 |
| “今年”跨立春，UTC时间输入 | 按既定北京时间边界显示；不自由改写日期 |
| 八字整岁与紫微虚岁并列 | 每个值有单位/口径；不合成统一年龄 |
| 无对方资料问合不合 | 澄清单人主题/双方关系；不假造对方盘 |
| 拆卡/面试活动 | 不自起盘，不从历法编概率；缺规则准确说明 |
| 六爻同事件重试/另问收款 | 同事件同盘；新事件须新确认；候选竞争不升确定 |
| 有正确盘但AI错误/核验拒绝 | 正确程序解释可见，失败块撤下，错误分层准确 |
| 模糊问题/转倾诉 | 澄清或接情绪；不强制新盘/重复填出生资料 |
| 恶意claimID/跨主体/旧版本注入 | 全部拒绝，不能只看引用格式合法 |
| 外部导入、账号切换、异步晚到 | 不恢复外部证据信任，不泄漏旧账号，不覆盖新状态 |
| AX最大字号、VoiceOver、深色、Reduce Motion | 逻辑阅读顺序、语义分组、按钮可辨，图有文本等价 |
| 云恢复/离线/超时/配额 | 准确解释恢复范围，报告独立可读，重试有上限 |

回归方法：先离线契约/生命周期/adapter/失效测试，再原生Hosted的报告→问道→历史链路；受授权后用上一轮32题同版本全量跑、逐题语义核对，并配真实输出原生回放。关键已知错误为固定反例，不以HTTP200/文本非空为通过。记录通过/澄清/诚实缺项/失败独立分母，缺项不提高“完成解读率”。可访问性须原生实际验证，文档评审不算通过。

## 14. 分阶段范围、依赖与风险

### P0 内容与协议底座（实施第一阶段）

先列全入口/出站/导入信任合同、单主体边界，再完成资料revision事务和operation generation，之后实现受审解释单元与强类型时间查询。盘点并隔离旧编辑文字；列可发布断言目录及缺口；重现当前错误的离线反例；统一动作预算与消息最小化。退出标准：P0信任和状态缺口有可执行协议，不能把旧personality当fact；跨主体/日期/导入错误可被程序约束；完成第3节内容样稿及门槛验证。通用Broker不作为这一步必要架构。

### P1 MVP：我的册页 + 带依据追问

本地基础报告、主题细读、依据层、专业入口、账号隔离/失效/离线、报告到命理问道binding（含草稿和运行中交接）、静态追问、错误局部保留。优先八字的一条完整可读路径，紫微保留专业盘及确已审定的基础说明；已有其余入口保留，不许暗示都已完整报告化。首发必须处理未建档退出、资料版本选择，以及动态/他人/事件/转倾诉的最小边界路由。

首批主题覆盖不以四个标题必须填满为硬要求；发布前要证明至少核心基础阅读有实际价值。换工作、关系等高级推断不算默认能力。无全量AI预生成、无运势总分、无后台每日重写、无新资源。

### P2 时间与场景扩展

时间范围chip、流年/运限强类型解释、更多经审象义、可靠的多轮场景讨论；将现有六爻/奇门结构化结果接入统一错误与历史视图，未补齐断法仍标缺项。

### P3 再评估

多体系并列解释、他人资料和关系场景、更丰富专业图解、可选AI固定文字个性化、多设备报告同步。独立星宿/七政体系解释需自己的方法/来源，不从本方案自动获得上线授权。

主要风险：内容审核比UI开发更慢；MVP过窄看起来像词典；自由场景文字仍可能夹带新断言；复杂失效模型增加维护；首次输入限制流失；全局建档gate改动影响权限；无云报告会有设备体验差异。缓解依靠小范围完整内容、明确分层和真实验收，不靠更多disclaimer。

## 15. 推荐默认与待决策

1. **首发内容承诺：**推荐以八字一条完整可读路径起步，并先补至少一个有来源的生活主题；紫微保留既有专业盘/经审说明。若只有读盘导读，作为内部试读，不把它当作用户要求的基础解读报告已经完成。需要产品负责人决定首个生活主题优先“自我观察”还是“工作与做事方式”；推荐自我观察，但仍以实际可审来源决定，不承诺先填性格标签。
2. **未建档访问政策：**推荐登录后允许稍后填写出生资料，今日/静心/普通倾诉可用，个人报告与个人命理需完成资料。这改变了之前“先填完才进入整个App”的门槛，应在实施授权时一并确认；不涉及允许匿名使用付费AI。
3. **入口推荐：**今日仍为全局首页，“我的”先呈现易读册页；首次完成建档可直接看一次册页。若要把报告改为主首页，应单独验证日历/静心用户是否受损。

不再把本地基础生成、按需AI、无总分、账号隔离等重复列成开放问题；它们是当前方案建议。云端完整报告同步、通用Broker与自由命理综合延后。

这些是少量产品取舍，实施前可由用户改动；其余账号隔离、证据有效性和不编造规则属于必要正确性条件，不交给用户选“开关”。本轮文档和独立评审完成后等待实施授权。

## 16. 这能修复当前哪些根因，哪些仍不能靠报告解决

| 已观察问题 | 方案针对的因果变化 | 不能夸大的部分 |
|---|---|---|
| 02追问漏取数、把历史文字当依据 | 静态确定解释直接读有效单元；模型路径程序执行缓存投影，不依赖planner碰巧调用 | 其他自然问法的主题识别仍需回归；现有02主问题尚未因此在代码里修好 |
| 已有盘面却显示全部无计算 | 强类型阶段状态区分计算、资料、能力、模型、核验；部分RenderUnit独立保留 | 不是单纯替换文案；若真实缺证据仍应明确失败 |
| 01/09错误字段、20/25日期、13/15年龄混用 | 字段和时间由程序渲染；TemporalQuery先解决范围；单位/限定不可拆 | 自由推理若继续绕过结构化合同仍会出错；不能只改system prompt宣告解决 |

验收必须看到这些因果变化的代码和输出证据，不能仅观察报告页更好看。上一轮32题结果不因本文修订而改变；后续同版本全矩阵、关键反例与人工语义复核仍是必需步骤。

## 17. 文档交付与后续顺序

冻结初稿、实际独立评审、逐项采纳表及终稿保存在同目录。推荐下一阶段授权范围先限于：**内容样稿与规则覆盖清点 → P0信任/资料生命周期协议 → 一条完整的报告到追问纵向MVP → 原生与真实问答验收**。不要先铺满四主题界面，再用AI临时填补内容。

本轮没有改业务代码、执行新模型矩阵、提交、合并或部署。方案完成不代表产品已实现；内容来源审核、可访问性实测、成本/延迟与新架构有效性仍待后续执行。
