## T-01 · P1：模块可展示状态与规则成立状态必须分开

**位置：**R1 §4 B4/B5、§5 `RuleAssertion.status` 与 `ReportModule.state`、§9 MVP 下限。

**具体反例：**某盘 `chengBai=jiuying`，局部一条 `rescuePaths.status=available-in-selected-profile`，但另一路仍 `unresolved-relative-strength`，全局明确 `unresolved`。适配器如果把模块 `ready` 或该局部 `available` 映射为“已得救应、格局成立”，每个字段都真的存在，结论仍越界。另一例：调候条目 `transcription-checked` 被当作“已替用户选定调候用神”。

**反对意见：**R1 的自然语言边界正确，但裸 `status` 尚不能防止上述映射。`ready` 只能表示有可呈现单元，不能表示命理结论成立；“未找到条件”也不能一律成为 `notApplicable`。

**替代方案：**在能力白名单中逐规则规定输入状态与允许句式，不使用一个通用布尔值。最低区分：事实已核对、规则子集成立、条件候选、反证成立、未决/来源冲突、未覆盖。另存范围 `local-path / selected-profile / whole-chart`，以及 `outcomeEstablished`；只允许缩小范围，不允许适配器自动升级。模块呈现状态独立：

- `notApplicable`：输入完整且所选规则的必要前提确实为假，应指出缺哪一项。
- `partial`：已有可解释事实，但某前提未知、竞争未决或部分内容尚未审完。
- `unsupported`：该解释能力没有已审核规则；不能让用户反复“重算”。
- `computeFailed`：计算或契约校验失败；不得用空数组伪装成“本盘没有”。

**验证办法：**用实际引擎夹具覆盖 `cheng/po/jiuying` 与候选总状态的组合、局部 available + 全局 unresolved、专旺规则子集成立 + `outcomeEstablished=false`、调候转录已核/未核。同字段改一个关键反证，主句必须撤回或降级。未决与前提为假的盘不得输出同一缺项句。未知状态应拒绝该规则单元，独立事实仍可读。

## T-02 · P1：来源、前提、排除条件与展示单元尚缺依赖闭包

**位置：**R1 §4.1、§5 `RuleAssertion` / `ContentUnit`、§6.2 部分结果保留。

**具体反例：**A 说“仅在所选位置与无根条件下，某局部作用受合牵制”；B 说“因此可采用这一条配合解释”。A 因新反证撤回，B 因仍引用合法 `sourceID` 留下。或者主句绑定已核对的干支，限定来自另一内容块；局部失败时“候选”限定被剔除。

**反对意见：**真实字段和来源哈希只证明引用对象存在，不证明新句子属于条文授权范围。`premises[FactRef] + exclusions` 还没说明：未知排除条件怎样传播、规则间冲突怎样阻止输出、摘要是否可以单独删限定。

**替代方案：**MVP 使用一个小型、静态登记的规则目录即可，不必上通用推理图。每条声明绑定 `sourceEditionID/sourceDigest/sourceAnchor/supportScope`、`evaluatorVersion`、准确的 premise/exclusion 谓词和允许的结论范围；前提三值为真/假/未知，未知不能当“无反证”。有派生时列 `dependsOnAssertionIDs` 和 `conflictsWith`，禁止循环；无审核跨模块规则则只并列比较，不生成“所以”。将主结论、必要条件、限定和年龄/时间口径组成不可分割的已审渲染单元，短版也各自审定。`reviewRecord` 是本地目录记录，不能由模型或外部导入授予。

**验证办法：**A→B→C 撤回链、A/B 互斥、排除条件未知、来源只支持定义但文案变成人格、摘要去掉“候选”、循环引用、未知 evaluator。每例分别检查屏幕、聊天正文、历史回放与图的文本替代，不能仅校验 JSON ID。保留独立 D，不用整页无结果掩盖局部错误。

## T-03 · P1：“真实投影或有效证据”需要具体接口，不能沿用事业代理

**位置：**R1 §5 `HandoffIntent`、§6.1 第1步、§8 ChatSession 复用。

**源码依据：**`ChatSession.answerTheme` 当前实际请求 `get_domain` 且 `domain=事业`；`BaziFrameworkReading.plan` 同样使用该参数。它们确实调用真实引擎并核对回执，不能说现有回执伪造；但这是局部历史耦合。`BaziThemeContext` 会重建当前主题再比较绑定，导航意图本身不构成计算依据。

**具体反例：**从 B1 日主模块发问，新的模块 ID 却仍拿事业投影做“全部依据已核实”；转到紫微时 adapter 找不到对应字段，退回旧 writer 或临时把本地事实写成 `ToolReceipt`。另一例：`HandoffIntent.validity=true` 从归档解码后直接授信，绕过当前主体和快照检查。

**替代方案：**终稿选择并说明最低可行接口：例如由现有本地引擎增加真正的 `report_module_projection` 命令/工具，或由原生可信仓库提供可核验的 `LocalFactEvidence` 类型。后者不伪装成工具执行回执；来源枚举明确区分真实工具与可信本地快照。无论选择哪种，都在信任入口核对 owner/subject、出生修订、bundle/payload/method、模块和消费字段，并返回版本化 projection manifest。静态追问可复用通过当前校验的本命事实，不必因新一轮或跨日重新算盘；真实新计算才产生新工具回执。`HandoffIntent` 永远只是意图，`validity` 应由本地验证器现场产生，不能作为 caller 提供的授权字段。

**验证办法：**B1/B3/B4/B5 各自的真实投影与字段白名单、跨模块误用、伪造当前 snapshotID、外部回执重算正确哈希、静态跨日复用、算法变更拒绝复用。记录实际工具名/参数或 LocalFactEvidence 来源，不把所有行记作“get_domain 成功”。同时保留现有硬编码路径测试，直到新合同完整替代，不能改名后删掉失败历史。

## T-04 · P1：主体、时间与事件应是不同的证据范围，不是若干可空字段

**位置：**R1 §5、§6 三入口、§6.1 链路、§7 跨日及他人问题。

**具体反例：**“明年也一样吗？”中的“明年”被解析为当前年份+1，但上一轮其实选过另一个年份；同一个时间字样在八字立春与紫微农历年下不是同一层。报告来自本人，却因“他呢”沿用当前主体。重试六爻问题时 eventID 换新，用户以为重试答复，实际重新起卦。

**反对意见：**R1 已指出这些边界，但 `requestedPeriod/asOf/method` 仍偏结果描述，没有解析来源和优先级。现有 `ToolContext` 不是通用多主体/多期间合同，添加 moduleID 不能自动补齐。

**替代方案：**先收窄为“单账户本人本命” MVP；他人盘请求明确澄清，不先开发关系仓库。范围采用带类型的分支：`natal(subjectRevision)`、`period(TemporalQuery, methodRange)`、`event(eventID, confirmedInputs)`；现实经历另为用户自述，不能成为推算证据。时间查询保留原问片段、冻结参考时刻、绝对/相对/回指来源、历法/时区及歧义状态。已确认重试冻结原范围与起局；新的问题才重新解析。最新明确的主体/事件请求覆盖历史焦点；“和同事讨论”仅有角色词，不证明在问同事的盘。

**验证办法：**模块→格局→跨模块→“明年也一样吗”→明确年份→六爻事件→“他呢”，逐步检查真正采用的 scope。补立春/农历年/午夜两侧、今年绝对年标签、同生日不同 subject、本人经历与他人命盘、重试不重抽盘；各条独立记录澄清或实际调用，不能只看路由 enum。T05 现状仍失败，不以这条设计链替换实测结果。

## T-05 · P1：一次修复不是整次咨询预算，标准路径仍可产生多重调用

**位置：**R1 §6.2、§10。

**源码依据：**`ToolOrchestrator` 默认最多5轮规划、8次工具；`ReadingVerifier.verify` 有两稿，每稿最多两次核验，中间还可重写。当前主题闭合选择最多两次请求，但这一上限不能覆盖退回标准路径后的全部动作。T05 的一次用户动态问题实际用了8次模型请求仍未完成解读。

**具体反例：**三个模块各自“一次修复”，再加路由、补数及旧 verifier；用户只按一次发送却叠加多轮请求，最后限流错误被误当能力缺项。取消后重试又从零开始，日志无法解释同一次问题的总成本。

**替代方案：**定义唯一 `UserActionBudget` 所有者，actionID 贯穿路由、选择、补数、核验、修复与取消；分别计模型尝试、工具次数、输入/输出 token、总截止时间。闭合模块路径可采用“初次选择+最多一次协议修复”的上限；跨模块仍共同消费该动作预算，不能每块开一个循环。标准动态路径保留独立能力/失败声明和明示上限；预算不足不能跳过核验。重试是继续失败步骤还是新动作必须写清，重试不自动改变已确认事件。具体真实批次数与费用授权另行制定，本文不追加调用额度。

**验证办法：**固定客户端依次返回无效JSON、合法但不答题选择、核验拒绝、429、超时、取消；检查所有阶段实际计数与截止时间，任何嵌套都不超限；仅保留已验证单元。真实批次必须同时报告用户轮数、模型请求数、工具次数，不能把19轮/19模型调用的旧主题批次当作每条入口均只调用一次。

## T-06 · P2：出生运行代际已加强，但不能把它写成持久化建档事务

**位置：**R1 §5 生命周期、§7 修改资料、§8 安全底座。

**源码依据：**`AppStore.updateBirth:220` 先保存新 `state.birth` 和待同步标记，随后更新运行时 `birthRevision`、取消任务并计算。`ensureNatalDossier`、`ChatSession.checkScope` 和 `ReflectionSession.checkScope` 已检查出生代际；当前 `hasNatalDossier`/编译器会比对出生与版本。**上一轮“只有出生值相等、A→B→A不区分”的问题不能照搬为当前未修。** 但 `birthRevision` 是运行时 UUID，重启后变更；它并非稳定的资料修订号或本地原子 promote/outbox。

**具体反例：**新资料保存后计算失败或应用退出，下次进入是新资料但尚无其有效报告。若产品文案承诺“修改未完成仍是完整旧档”，就与实现不符。反过来，不能把旧本命快照匹配失败称作旧资料丢失。若把运行 UUID 当永久 revision 存入历史，新启动会使所有可追问引用失效，未必是用户预期。

**替代方案：**MVP可沿用“先确认资料，再进入待计算/失败状态”以避免不必要的大事务重构，但终稿必须明确这一承诺：当前资料版本可用、旧报告只读且标过期、当前问道不能借用旧证据、输入保留、重算可恢复。将运行 `operationGeneration` 与持久化 `birthInputRevision` 分清；若暂不增加持久化修订，以出生指纹+可信来源重建新会话，不宣称跨启动保留原授权。若要“整份档案计算成功才替换”的产品体验，必须另做事务设计，不能只改字段名。云端在途写冲突仍单列未验证。

**验证办法：**各保存点失败/退出后重启，B资料算失败时旧A不能成为当前；A→B→A晚到、同值重新确认、重启后新建绑定、旧历史仍可读、账号切换；新报告内容版本改变不重算天文。对跨设备/outbox未实测部分明确标记，不以已过的本地 generation 测试替代。

## T-07 · P2：局部失败隔离要先拆解码和信任边界，不能只在 View 中加状态

**位置：**R1 §5 最后一段、§7 首次算盘、§9 五模块范围。

**源码依据：**`NatalReadingCompiler.natal` 解码单个 `NatalReadingInput`，其 `mingPan` 与 `ziweiPan` 均必需；一次 `chart.validate` 后在同一 `try` 中生成两个体系。B4/B5若新增为必需字段，坏调候条目可能使整盘基础四柱也不可读。天文侧当前也共用验证和报告生成。

**具体反例：**某紫微宫星字段异常，使八字所有模块显示“无结果”；某 B4 条件来源哈希过期，把已核对日干/月支一起隐藏。UI 即使有 `ReportModule.partial`，上游根本没生成它。

**替代方案：**按“共享 envelope 身份/出生/版本 → 体系基础事实 → 模块规则 → 内容”分层验证。共享身份不一致需拒绝所有依赖；只有某体系/规则失败则输出可定位的失败原因，其他已核对事实独立保留。模块不能用 optional 默认空值吞错误。共享计算数据不必重复存四份，通过消费字段与依赖 manifest 隔离即可。

**验证办法：**逐个篡改紫微字段、B4来源、B5调候状态、公共birthKey和引擎版本，断言受影响范围；公共出生损坏应全部拒绝，B5内容缺项不应让B1消失。错误/离线恢复实际走 production compiler，不能只用 mock `partial` 测 View。

## T-08 · P1：现代建议、旧历史与 Reflection 必须有出站边界

**位置：**R1 §6.2 现代建议、§7 隐私、§8 Reflection 旁路。

**具体反例：**模型把“你描述工作中不敢提意见”改写为“这也印证伤官受制，因此应选择自由职业”，每句都标成现代建议就穿过了闭合命理约束。用户从册页转入原问道，历史里另一人的信息被 `ReadingPrompt.history` 的最近20条规则带出。新模块事实若沿用普通字符串传给 Reflection，后者会直接流式显示未经命理核验的生成文本。

**源码依据：**`ReadingContext.swift:95` 目前按条数/字节取历史，不是按模块/主体授权筛选；`ReflectionSession.run` 在有账号/出生隔离的前提下，仍把 context 拼入系统消息并直接 `streamText`。它不是完全没有保护，缺的是新命理主张的证据合同。当前主题路径没有调用它，这一点值得保留。

## 2. 对“是否已经能做参考级解释”的判断

### R2-T10 · P2：stale与computeFailed的恢复动作不能由同一按钮文案替代

§5概览仍写“computeFailed才可重算”，但下一段说出生/口径/引擎变化失效，§5.5又允许新资料报告待计算。这两者并不相容：出生修订后的`stale`可能确实需要重算；内容版本变化只需重编，不该重新跑天文。

建议将这句改成“恢复动作按具体失效原因选择”，并列出：出生/算法/历法变更→查当前合法缓存或重算；内容/evaluator更新→重评适用规则/重编内容，若事实消费需求变了才补算；网络失败→重试在线阶段；前提为假/能力缺项→解释缺口，不反复重算；契约失败→诊断后有界重新取数。未来用这几种stale原因各做一个用例，不能只断言都出现“重试”。本轮未执行这些用例。

### R2-T11 · P2：顶层revision命名需与“不新增持久化revision”一致

§5仍有`SubjectScope.birthRevision`，§5.4有`natal(subjectRevision)`，§5.5则明确只用运行`operationGeneration`与稳定出生指纹、不新增持久化revision。可按后文理解，但实施者可能把同名字段一处当UUID、一处当历史资料版本号，导致重启后错误恢复授权或额外造表。

建议在伪契约旁直接注明：本人MVP的subjectRevision是“owner内稳定本人身份+当前出生指纹+当前运行代际”的复合身份，不承诺可持久化的历史版本序号；若沿用现有birthRevision名称，它就是运行代际别名，重启不复活旧binding。旧正文只读与当前新绑定明确分开。未来测试启动前后同一出生输入应复用有效计算，同时创建新运行授权；跨账号即使同出生指纹也不能授信。
